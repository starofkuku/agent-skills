# 通俗改动汇报

把代码改动翻译成不懂技术的人也能看懂的话。

汇报范围由参数决定，**无参数时汇报工作区里还没提交的改动**。

## 参数

| 调用 | 汇报范围 |
| ---- | -------- |
| `$plain-change-report` | 工作区里未提交的改动（默认） |
| `$plain-change-report --since v1.1.0` | 自 `v1.1.0` 以来到当前 |
| `$plain-change-report --since a1b2c3d` | 自某个提交以来到当前 |
| `$plain-change-report --commits a1b2c3d e4f5a6b` | 指定的这些提交（可非连续） |
| `$plain-change-report --last 5` | 最近 5 次提交 |

- `--since` 与 `--commits` 的值可以是**提交号、tag、分支名**。
- `--commits` 可以跟多个，顺序不限。
- `--last` 只接受 **≥1 的整数**；不是整数或小于 1 时直接报错，不要瞎猜。
- 三个参数**互斥**，一次只用其中一个。
- 各模式的精确命令、边界处理和已踩过的坑见 [references/git-ranges.md](references/git-ranges.md)。

## 边界

- **只读不改。** 不提交、不推送、不改动任何被跟踪的文件，也不顺带改代码。
- 唯一写入的文件是仓库根目录的 `CHANGE-REPORT.local.md`，且会被加入 `.git/info/exclude`，不进改动清单。
- 报告只描述**已经存在的**改动，不替读者决定该不该上线。

## 核心原则

- **读者不懂技术。** 报告里出现的每个词，都应该是他能理解或能感知的。
- **写最终结果，不写过程。** 报告描述的是**这批改动结束后的最终状态**。中途加过又删掉的东西，不要出现在报告里。
- **只讲事实。** 只写代码能证明的事；判断不出对使用者的影响时，写「内部调整，使用者看不到变化」。
- **宁可保守。** 拿不准的影响不写，不要为了凑内容把内部整理说成新功能。
- **先说结果。** 先告诉读者「改完他能感受到什么」，而不是「动了哪些地方」。

## 执行流程

### 1. 确定范围并校验

先按参数取出范围。**任何 ref 都要先校验存在**，不存在就停下来问，不要退化成默认模式：

```bash
git rev-parse --verify --quiet "<ref>^{commit}"
```

各模式的完整命令见 [references/git-ranges.md](references/git-ranges.md)。三条硬要求：

- 未提交模式必须用 `git status --porcelain=v1 -uall`，**不带 `-uall` 时新增目录会被折叠成一行目录名，里面的文件全部看不见**。
- **未跟踪的新文件不出现在 `git diff` 里**，必须单独读文件内容。这是最容易漏的一整类改动。
- 多提交范围要取**净变化**（一次 diff），不要逐个提交各写一段。

### 2. 收集改动

按范围读取改动内容。diff 很大时按文件分批看，不要把全量 diff 一次性读进上下文。

图片、二进制、锁文件没有可读 diff，按「替换了一个资源/依赖锁定文件」处理，归入「其他调整」。

### 3. 剔除不该进报告的改动

- 本 skill 自己上一轮产出的 `CHANGE-REPORT.local.md`，忽略。
- 构建产物、缓存、日志、依赖锁文件：合并成一条，不要逐条罗列。
- 纯格式变动（缩进、换行、排序）：合并成一条「内部整理，功能没有变化」。
- 已被后续修改推翻的中间态：不写。

### 4. 逐处翻译成「对使用者意味着什么」

对每处改动只回答一个问题：**这件事做完，谁能感觉到不同？**

| 判断 | 写法 |
| ---- | ---- |
| 能感觉到 | 直接写这个变化本身 |
| 感觉不到 | 写「内部调整，使用者看不到变化」 |
| 判断不了 | 写「内部调整，需要技术同事确认影响」，不要猜 |

代码改动 → 通俗说法的对照表、模块命名方式、措辞黑名单和正反例见 [references/plain-language.md](references/plain-language.md)。

### 5. 归类与措辞

两个层次：**先按大类分，再在每条前面标注模块。**

大类只保留有内容的，空的不要写（不要出现「本次无新增功能」这类噪音）：

| 大类 | 适用 |
| ---- | ---- |
| 新增功能 | 出现了以前没有的能力 |
| 问题修复 | 修掉了以前会出错、卡住、显示不对的地方 |
| 体验优化 | 功能没变，但更快、更好用、更顺 |
| 其他调整 | 内部整理、配置、文档、依赖更新等 |

模块用 `【模块】` 标注，取业务语言（`【登录】`、`【订单】`、`【首页】`），**不要用目录名、文件名**。推断不出来就用 `【通用】`。

### 6. 写入并排除报告文件

先确保报告文件不会被误提交，再写：

```bash
git check-ignore -q CHANGE-REPORT.local.md || \
  echo "CHANGE-REPORT.local.md" >> "$(git rev-parse --git-dir)/info/exclude"
```

用 `.git/info/exclude` 而不是 `.gitignore`：不修改被跟踪的文件，报告文件本身也就不会出现在改动清单里；该命令可重复执行，不会产生重复行。

### 7. 报告模板

````markdown
# 本次改动说明

本次说明覆盖 2025-05-01 至 2025-06-10 的 7 次更新。

（一句话说清这次整体在做什么，不要罗列技术细节）

## 新增功能

- 【订单】客户可以直接下载电子发票

## 问题修复

- 【登录】以前手机上输完密码按钮点不动，现在可以正常登录

## 体验优化

- 【首页】打开速度变快

## 其他调整

- 更新了内部说明文档，使用者看不到变化

## 需要留意

- 上线后需要重新发布
- 建议重点验证：手机上的登录流程
- 无需更新数据库
````

第二行「覆盖范围」按模式写：

| 模式 | 这一行写成 |
| ---- | ---------- |
| 未提交改动 | 本次说明覆盖尚未提交的改动。 |
| 区间 / 最近 N 次 | 本次说明覆盖 `<首日>` 至 `<末日>` 的 `<N>` 次更新。 |
| 指定提交 | 本次说明覆盖 `<首日>` 至 `<末日>` 的 `<N>` 次更新。（N = 列出的提交数） |

日期取 `--date=short`，**用日期和次数，不要出现提交号、分支名、tag 名**。

### 8. 没有改动时

范围内没有任何改动时，直接回答「该范围内没有改动，无需汇报」（未提交模式：「当前没有未提交的改动，无需汇报」）并停止，**不要凭空生成报告**。

## 措辞硬规则

报告里**不允许出现**：

- 文件名、目录路径、函数名、类名、变量名、包名
- 接口名、字段名、表名、字段类型
- 提交号、分支名、tag 名、issue 编号
- 框架名、库名、语言名
- 「重构」「抽象」「依赖注入」「并发」「异步」「中间件」「序列化」等工程术语
- 「修复了 bug」「优化了性能」这类只给结论、不给现象的空话

必须做到：

- 每条写一个**可观察的现象**：哪个地方、发生了什么变化
- 一条一句话，控制在 30 字左右
- 修问题要写清「原来什么样、现在什么样」
- 影响不确定就写「需要技术同事确认」，不要写死

## 需要留意

最后一节的内容必须能从改动本身看出来，不允许凭印象推断：

| 改动里出现 | 可以写 |
| ---------- | ------ |
| 数据库迁移脚本、建表/改表语句 | 「需要更新数据库」 |
| 前端页面、样式 | 「上线后需要重新发布前端」 |
| 后端服务代码 | 「上线后需要重新部署服务」 |
| 只有文档、注释 | 「无需重新发布」 |
| 判断不了 | 「需要技术同事确认上线方式」 |

「建议重点验证」只写改动直接涉及的功能：改了登录就写「建议重点验证手机上的登录流程」，不要泛泛写「建议全量回归测试」。

## 自检清单

报告写完逐条过一遍：

1. 每个词，不懂技术的人能看懂吗？——有一条看不懂就要改。
2. 每条都是一个**能观察到的现象**吗？——不是就重写。
3. 有没有把内部整理说成新功能？——有就降级到「其他调整」。
4. 有没有中途加过又删掉、已经不存在的东西？——删掉。
5. 有没有编造代码里看不出来的影响？——有就删掉或改成「需要技术同事确认」。
6. 空的大类是不是还留在报告里？——删掉。
7. 「需要留意」里的每条，都能从改动本身看出来吗？——不能就删。
