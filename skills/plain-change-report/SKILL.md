# 通俗改动汇报

把代码改动翻译成不懂技术的人也能看懂的话。汇报范围由参数决定，**无参数时汇报工作区里还没提交的改动**。

## 参数

| 参数 | 作用 |
| ---- | ---- |
| 无 | 未提交的改动（默认） |
| `--since <ref>` | 自某个 tag / 提交以来到**当前 HEAD**（进展视角，含 tag 之后的新提交） |
| `--from <tag> [--to <tag>]` | **两次发布之间**的变化：`--from` 到 `--to` 的净变化（发布对比视角）。`--to` 省略时取**同前缀**系列里最新的发布 tag（`ieioms-v0.0.1` → 在 `ieioms-v*` 里找；`v0.0.3` → 在 `v*` 里找） |
| `--commits <ref>...` | 指定的这些提交（可非连续） |
| `--last <N>` | 最近 N 次提交 |
| `--repo <名字>` | 限定只汇报哪几个仓库，逗号分隔或多次传 |

示例：

```text
$plain-change-report
$plain-change-report --since v1.1.0
$plain-change-report --from v0.0.1 --to v0.0.2
$plain-change-report --from v0.0.1                 # 到最新 tag
$plain-change-report --commits a1b2c3d e4f5a6b
$plain-change-report --last 5
$plain-change-report --repo admin-front,backend          # 未提交模式 + 限定仓库
$plain-change-report --repo admin-front,backend --since v1.1.0
```

- `--since` / `--commits` 的值可以是**提交号、tag、分支名**；范围参数（`--since` / `--from` / `--last`）**互斥**，一次只用一个。
- `--from/--to` 配合 `publish-merge` 的自动 tag 使用：每次合并到主分支会自动打递增 tag，用 `--from <上一个tag> --to <本次tag>` 就能总结这次发布引入的全部变化。
- `--from` / `--to` 两端解析结果（含 `--to` 省略时实际取到的 tag）必须先在**对话里**报出来再写报告。
- `--last` 只接受 **≥1 的整数**，不是就报错，不要猜。
- `--repo` 是修饰参数，可与任意范围参数组合，也可单独用。按**目录名**匹配，不匹配任何仓库时把不匹配的名字报给调用者。
- 各模式的精确命令、边界处理和已踩过的坑见 [references/git-ranges.md](references/git-ranges.md)。

## 边界

- **只读不改。** 不提交、不推送、不改动任何被跟踪的文件，也不顺带改代码。
- 唯一写入的文件是**工作区根目录**（调用时的当前目录）下的 `CHANGE-REPORT.local.md`。
- 报告只描述**已经存在的**改动，不替读者决定该不该上线。

## 核心原则

- **读者不懂技术。** 报告里出现的每个词，都应该是他能理解或能感知的。
- **写最终结果，不写过程。** 报告描述的是这批改动结束后的**最终状态**，中途加过又删掉的东西不出现。
- **一个功能一条，不分仓库。** 同一个功能在前端仓库和后端仓库的改动，合并成一条。读者不关心代码放在几个仓库里。
- **只讲事实。** 只写代码能证明的事；判断不出影响时写「内部调整，使用者看不到变化」。
- **宁可保守。** 拿不准的影响不写，不要为了凑内容把内部整理说成新功能。
- **先说结果。** 先告诉读者「改完他能感受到什么」，而不是「动了哪些地方」。

## 执行流程

### 1. 判定工作区模式并确定仓库清单

把**调用时的当前目录**作为工作区根目录，不要自动替换成 Git 根目录。

```bash
git rev-parse --show-toplevel
```

| 情况 | 模式 | 汇报对象 |
| ---- | ---- | -------- |
| 当前目录在某个 Git 仓库内 | 单仓库 | 该仓库 |
| 不是仓库，但子目录里有 Git 仓库 | 多仓库 | 按下面的规则筛选 |
| 都不是 | 报错停止 | —— |

多仓库模式下先找出全部子仓库：

```bash
find . -mindepth 2 -maxdepth 3 -name .git -not -path '*/node_modules/*' \
  | xargs -n1 dirname | sort
```

再按参数确定纳入清单：

- **给了 `--repo`**：只纳入目录名匹配的仓库，其余即使有改动也不管。
- **没给 `--repo`**：逐个查 `git -C <repo> status --porcelain=v1 -uall`，**只纳入有改动的仓库**，干净的跳过。

纳入清单必须先在**对话里**说清楚（例：「本次汇报纳入：admin-front、backend；portal-front 无未提交改动，已跳过」），再开始写报告。清单为空时按「没有改动」处理。

从单个仓库内部调用时就是单仓库模式；要跨仓库汇报，到共同父目录调用。

### 2. 确定范围并校验

**任何 ref 都要先校验存在**，无效就停下来问，不要静默退化：

```bash
git rev-parse --verify --quiet "<ref>^{commit}"
```

多仓库 + 范围参数时，**逐仓库校验**：没有该 ref 的仓库跳过（前后端 tag 不同步是常态），并把跳过原因写进对话。全部仓库都没有该 ref 时报错停止。

三条硬要求：

- 未提交模式必须用 `git status --porcelain=v1 -uall`，**不带 `-uall` 时新增目录会被折叠成一行目录名，里面的文件全部看不见**。
- **未跟踪的新文件不出现在 `git diff` 里**，必须单独读文件内容。这是最容易漏的一整类改动。
- 多提交范围要取**净变化**（一次 diff），不要逐个提交各写一段。

### 3. 收集改动

按范围逐仓库读取改动，全部命令加 `git -C <repo>`。diff 很大时按文件分批看，不要把全量 diff 一次性读进上下文。

图片、二进制、锁文件没有可读 diff，按「替换了一个资源/依赖锁定文件」处理，归入「其他调整」。

### 4. 剔除不该进报告的改动

- 本 skill 自己上一轮产出的 `CHANGE-REPORT.local.md`，忽略。
- 构建产物、缓存、日志、依赖锁文件：合并成一条，不要逐条罗列。
- 纯格式变动（缩进、换行、排序）：合并成一条「内部整理，功能没有变化」。
- 已被后续修改推翻的中间态：不写。

### 5. 逐处翻译成「对使用者意味着什么」

对每处改动只回答一个问题：**这件事做完，谁能感觉到不同？**

| 判断 | 写法 |
| ---- | ---- |
| 能感觉到 | 直接写这个变化本身 |
| 感觉不到 | 写「内部调整，使用者看不到变化」 |
| 判断不了 | 写「内部调整，需要技术同事确认影响」，不要猜 |

代码改动 → 通俗说法的对照表、模块命名方式、措辞黑名单和正反例见 [references/plain-language.md](references/plain-language.md)。

### 6. 归类与合并

两个层次：**先按大类分，再在每条前面标注模块。** 大类只保留有内容的，空的不要写：

| 大类 | 适用 |
| ---- | ---- |
| 新增功能 | 出现了以前没有的能力 |
| 问题修复 | 修掉了以前会出错、卡住、显示不对的地方 |
| 体验优化 | 功能没变，但更快、更好用、更顺 |
| 其他调整 | 内部整理、配置、文档、依赖更新等 |

模块用 `【模块】` 标注，取业务语言（`【登录】`、`【订单】`、`【首页】`），**不要用目录名、文件名、仓库名**。推断不出来就用 `【通用】`。

**多仓库时报告绝不按仓库分节。** 跨仓库合并规则：

- 同一个【模块】、同一个用户可见现象 → **合并成一条**。典型：前端加了下载入口 + 后端加了对应处理 → 只写「【订单】客户可以下载电子发票」。
- 只有单侧改动 → 正常写一条。
- 判断不了两边是不是同一个功能 → **分开写，宁可两条也不错并**。

### 7. 写入报告文件

报告写入工作区根目录的 `CHANGE-REPORT.local.md`。先确保它不会被误提交——**仅当工作区根目录本身在某个 Git 仓库内时**才需要排除：

```bash
if git rev-parse --show-toplevel >/dev/null 2>&1; then
  git check-ignore -q CHANGE-REPORT.local.md || \
    echo "CHANGE-REPORT.local.md" >> "$(git rev-parse --git-path info/exclude)"
fi
```

- 用 `git rev-parse --git-path info/exclude`，它能正确处理 `.git` 是文件的情况（worktree、submodule），不要用 `--git-dir` 自己拼路径。
- 多仓库模式下工作区根目录通常不是 Git 仓库，此时**什么都不用排除**，也不要去改子仓库的 exclude——报告文件不在它们的管辖范围内。
- 该命令可重复执行，不会产生重复行。

### 8. 报告模板

````markdown
# 本次改动说明

本次说明覆盖 2025-05-01 至 2025-06-10 的 7 次更新。

（一句话说清这次整体在做什么，不要罗列技术细节）

## 新增功能

- 【订单】客户可以直接下载电子发票

## 问题修复

- 【登录】以前手机上输完密码按钮点不动，现在可以正常登录

## 体验优化

- 【首页】打开速度变快

## 其他调整

- 更新了内部说明文档，使用者看不到变化

## 需要留意

- 上线后需要重新发布
- 建议重点验证：手机上的登录流程
- 无需更新数据库
````

「覆盖范围」一行按模式写，**只出现日期和次数**：

| 模式 | 这一行写成 |
| ---- | ---------- |
| 未提交改动 | 本次说明覆盖尚未提交的改动。 |
| 区间 / 最近 N 次（单仓库） | 本次说明覆盖 `<首日>` 至 `<末日>` 的 `<N>` 次更新。 |
| 区间 / 最近 N 次（多仓库） | 同上；首日取各仓库最早的，末日取最晚的，次数是各仓库之和。 |
| 指定提交 | 本次说明覆盖 `<首日>` 至 `<末日>` 的 `<N>` 次更新。（N = 列出的提交数） |

日期取 `--date=short`。**报告文件里不出现提交号、分支名、tag 名、仓库名**；仓库名只出现在对话输出的纳入清单里。

### 9. 没有改动时

范围内没有任何改动时，直接回答「该范围内没有改动，无需汇报」并停止，**不要凭空生成报告**。多仓库模式下所有纳入仓库都没有改动时同理，并把逐仓库情况在对话里说明。

## 措辞硬规则

报告里**不允许出现**：

- 文件名、目录路径、函数名、类名、变量名、包名
- 接口名、字段名、表名、字段类型
- 提交号、分支名、tag 名、issue 编号、**仓库名/目录名**
- 框架名、库名、语言名
- 「重构」「抽象」「依赖注入」「并发」「异步」「中间件」「序列化」等工程术语
- 「修复了 bug」「优化了性能」这类只给结论、不给现象的空话

必须做到：

- 每条写一个**可观察的现象**：哪个地方、发生了什么变化
- 一条一句话，控制在 30 字左右
- 修问题要写清「原来什么样、现在什么样」
- 影响不确定就写「需要技术同事确认」，不要写死

## 需要留意

最后一节的内容必须能从改动本身看出来，不允许凭印象推断：

| 改动里出现 | 可以写 |
| ---------- | ------ |
| 数据库迁移脚本、建表/改表语句 | 「需要更新数据库」 |
| 前端页面、样式 | 「上线后需要重新发布前端」 |
| 后端服务代码 | 「上线后需要重新部署服务」 |
| 只有文档、注释 | 「无需重新发布」 |
| 判断不了 | 「需要技术同事确认上线方式」 |

多仓库时按实际改动的仓库判断：只有后端仓库变了就只写「需要重新部署服务」，不要把没动的前端也写上。

「建议重点验证」只写改动直接涉及的功能，不要泛泛写「建议全量回归测试」。

## 自检清单

报告写完逐条过一遍：

1. 每个词，不懂技术的人能看懂吗？——有一条看不懂就要改。
2. 每条都是一个**能观察到的现象**吗？——不是就重写。
3. 有没有把内部整理说成新功能？——有就降级到「其他调整」。
4. 有没有中途加过又删掉、已经不存在的东西？——删掉。
5. 同一个功能有没有在前后端各写一条？——合并成一条。
6. 报告里有没有出现仓库名、目录名？——删掉（对话里可以有）。
7. 有没有编造代码里看不出来的影响？——有就删掉或改成「需要技术同事确认」。
8. 空的大类是不是还留在报告里？——删掉。
9. 「需要留意」里的每条，都能从改动本身看出来吗？——不能就删。
