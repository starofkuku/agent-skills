# 通俗表达对照表

把代码改动翻译成非技术读者能懂的句子。左边是改动长什么样，右边是可以直接写进报告的说法。

## 判断入口

每处改动先问一句：**这件事做完，谁能感觉到不同？**

- 普通使用者能感觉到 → 写他感受到的变化
- 只有内部同事能感觉到 → 写「内部调整」+ 谁受益
- 谁都感觉不到 → 合并进「其他调整」，一句话带过

## 常见改动对照

### 界面与交互

| 改动 | 写成 |
| ---- | ---- |
| 新增页面、弹窗、按钮 | 新增了某个入口，可以做什么事 |
| 表单加了必填校验 | 提交前会提示哪一项没填，减少填错 |
| 加了加载中、骨架屏 | 等待时界面不再是一片空白 |
| 加了成功/失败提示 | 操作完能立刻知道有没有成功 |
| 调整了布局、间距、配色 | 界面排版更整齐（能看出变化时才值得写） |
| 文案改写 | 提示语更清楚了 |
| 补充了空状态 | 没有数据时会告诉用户为什么空 |
| 手机端适配 | 手机上显示不再错位 |

### 功能行为

| 改动 | 写成 |
| ---- | ---- |
| 新增查询、筛选、搜索 | 可以按某个条件快速找到需要的记录 |
| 新增导出、下载 | 可以把结果导出成文件带走 |
| 新增批量操作 | 可以一次处理多条，不用一条条点 |
| 新增权限控制 | 不同的人只能看到自己该看的内容 |
| 新增审批、通知 | 到达某个环节会自动通知相关的人 |
| 去掉某个入口 | 移除了某个不再使用的功能 |
| 流程步骤减少 | 原来要点好几步，现在一次就能完成 |

### 错误修复

修问题必须写清「原来什么样、现在什么样」。

| 改动 | 写成 |
| ---- | ---- |
| 空值判断缺失 | 以前某项没填会报错，现在会给出提示 |
| 边界条件修了 | 以前超出常规范围的数据会显示错误，现在正常 |
| 并发/重复提交 | 以前快速点两下会重复提交，现在只生效一次 |
| 时间/时区 | 以前时间会差几小时，现在显示正确 |
| 中文乱码、编码 | 以前中文会显示成乱码，现在正常显示 |
| 数字精度、金额舍入 | 以前金额会有零点几分的偏差，现在准确 |
| 权限判断遗漏 | 以前不该看到的人也能看到，现已限制 |
| 缓存没更新 | 以前改完要刷新才生效，现在立刻能看到 |
| 分页、总数不对 | 以前列表条数统计不准，现在正确 |

### 性能与稳定性

| 改动 | 写成 |
| ---- | ---- |
| 加索引、优化查询 | 打开列表变快，等待时间变短 |
| 加缓存 | 重复访问时明显更快 |
| 减少重复请求 | 页面打开时不再重复加载，消耗更低 |
| 压缩、懒加载 | 首次打开更快，流量更省 |
| 加重试、容错 | 偶发故障时会自动重试，不容易白屏 |
| 加日志、监控 | 出问题时能更快定位（内部受益） |

### 内部调整（使用者看不到变化）

| 改动 | 写成 |
| ---- | ---- |
| 拆分文件、调整结构 | 内部整理，功能没有变化 |
| 改命名、抽公共代码 | 内部整理，方便后续维护 |
| 升级依赖、换库 | 更新了底层组件，使用者看不到变化 |
| 补注释、写文档 | 补充了内部说明文档 |
| 加测试 | 增加了自动检查，后续改动更不容易出错 |
| 加配置项、环境变量 | 调整了部署配置，需要重新发布才生效 |
| 改构建、流水线 | 调整了打包发布流程 |
| 数据库迁移脚本 | 需要更新数据库，由技术同事执行 |

### 资源与文件

| 改动 | 写成 |
| ---- | ---- |
| 换图片、图标、Logo | 更新了某个图标/图片 |
| 换字体 | 文字显示效果有调整 |
| 加多语言 | 支持了新的语言 |
| 加说明文件 | 补充了使用说明 |

## 模块命名

用**业务语言**，取自产品实际叫法，不要用目录名或文件名。

| 不要写 | 应该写 |
| ------ | ------ |
| 【src/views/user】 | 【用户中心】 |
| 【UserController】 | 【用户管理】 |
| 【api/auth】 | 【登录】 |
| 【components/Table】 | 【列表页】 |
| 【utils/date】 | 【通用】 |

判断不出来时用 `【通用】`。**一个模块名反复出现说明改动集中在那一块，这是好事，不用为了平均而硬凑别的模块。**

## 跨仓库合并（前后端分仓 / 多前端共一后端）

同一个功能往往前后端各改一部分，报告里**只能有一条**，从读者视角描述。判断两处改动是不是同一个功能的线索：

| 线索 | 例子 |
| ---- | ---- |
| 模块标签相同 | 两边都是【订单】 |
| 业务名词相同 | 两边都出现「发票」「审批」「库存」 |
| 用户看到的现象是同一件事 | 前端加了下载入口，后端加了对应处理 → 都是「能下载发票了」 |
| 提交时间相近（范围模式） | 同一天的提交 |

**反例（错并）**：前端加了【首页】轮播图，后端同时修了【订单】金额计算——模块不同、现象不同，必须各写一条，不能因为「都是这次改的」就合并。

**典型正例**：

```text
仓库 A（前端）：订单详情页新增「下载发票」按钮
仓库 B（后端）：新增发票生成与下载处理

报告只写一条：
## 新增功能
- 【订单】客户可以直接下载电子发票
```

拿不准两边是不是同一个功能时，**分开写两条**。错并（把两个功能说成一个）比多写一条严重得多：读者会以为只改了一件事。

报告里也不出现「前端」「后端」「仓库」这些说法——读者不需要知道代码怎么分的，在报告里写「后端新增了接口」就是把实现细节满给了读者。

## 措辞黑名单

下面这些词一旦出现，报告就失败了：

```text
代码术语：接口 API 参数 字段 表 索引 缓存 中间件 依赖注入 重构 抽象
          并发 异步 同步 序列化 反序列化 钩子 组件 模块 类 函数 方法
技术名词：Vue React Java TypeScript Node 数据库 SQL Git 分支 提交 合并
          npm 构建 编译 部署 容器 服务 端口 环境变量
空洞结论：修复了 bug 优化了性能 完善了功能 提升了体验
          （只给结论不给现象，读者看完还是不知道改了什么）
```

## 正反例

**反例**

> 重构了订单模块的 Service 层，抽取 OrderValidator 校验订单状态，修复了并发下单时的库存超卖问题。

**正例**

> - 【订单】修好了有人同时下单导致库存变成负数的问题
> - 【订单】内部整理，后续维护更方便

**反例**

> 新增 GET /api/invoice/download 接口，前端 OrderDetail.vue 增加下载按钮。

**正例**

> - 【订单】客户可以在订单详情里直接下载电子发票

**反例**

> 优化了首页的图片加载，使用懒加载 + webp 格式。

**正例**

> - 【首页】打开速度变快，手机流量也更省

## 自检清单

报告写完逐条过一遍：

1. 每个词，不懂技术的人能看懂吗？——有一条看不懂就要改。
2. 每条都是一个**能观察到的现象**吗？——不是就重写。
3. 有没有把内部整理说成新功能？——有就降级到「其他调整」。
4. 有没有编造代码里看不出来的影响？——有就删掉或改成「需要技术同事确认」。
5. 空的大类是不是还留在报告里？——删掉。
6. 「需要留意」里的每条，都能从改动本身看出来吗？——不能就删。
